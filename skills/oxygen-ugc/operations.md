# OXYGEN UGC

Use when a product team wants creators to publish in their own voice, or a creator wants to join a program and write a post. UGC is a feature composing Knowledge, Posts and Publishing; it does not create another primitive or another physical LinkedIn connection.

## Start with identity and discovery

1. Verify the active host, user and workspace with `oxygen whoami --json`.
2. Discover `oxygen ugc --help` and `oxygen ugc programs list --json`. An unavailable response means the feature is disabled; do not work around its gate.
3. For MCP, discover the `ugc` toolset pack. `oxygen_ugc_get` reads each view; action tools use the exact `oxygen_ugc_` action names returned by capability search.

## Program operators

Setup is lean: a program needs only its product link. Create one with `oxygen ugc programs create --product-url "https://example.com" --json`. OXYGEN reads the product's homepage once, for free: the program is named after the site (its `og:site_name`, else its title, else the domain) and gets the site's icon as `icon_url`. Pass `--name "Acme"` to choose it yourself. Creators read it as the brand ("post about Acme" in their invitation), so name the brand, never "Acme Creator Program". An unreachable site never blocks creation; the program is then named after its domain. Program creation uses 0 credits and makes no provider call.

Give creators a brief with `--brief "<up to 4,000 characters>"` on create (Markdown headings, lists and links render for creators), or later with `oxygen ugc programs update --program-id <id> --brief "..." --json` (an empty string clears it). Write it yourself, plainly: what the product is, who it is for, three to five facts creators may state, and one call to action. Creator drafts take product facts from this brief first. Program reads return `brief` to the operator and to joined creators. A brief longer than 4,000 characters is refused: keep the facts and call to action in the brief and share the rest as a wiki page (below). Never move it into `--description`, an internal note creators never see and drafts never use.

Set the program's standard deliverable with `--posting-target 4/month` (posts per creator each calendar month), `--posting-target 2/week` or `--posting-target 10/total` (posts per creator over the whole program), 1–100, on create or update; `--posting-target none` clears it. There is no fortnight: 2 every two weeks is `1/week` (counted per calendar week, so a little stricter) or about `4/month`, never `2/month`, which is half the rate; tell the operator which you chose. It applies to every creator without a deal of their own.

When one creator agrees a different deal, record it on that creator, never by splitting them into a second program: add `--posting-target 1/month` to `oxygen ugc creators invite` (it applies to every recipient of that invite), or change it later with `oxygen ugc creators set-target --program-id <id> --participation-id <id> --posting-target 1/month --json` for a joined creator or `--invitation-id <id>` for a pending invitation; `--posting-target none` returns them to the program standard. Organizer only, free. `oxygen ugc creators list --program-id <id> --json` returns `program_posting_target` plus each creator's and each pending invitation's own `posting_target` (null means the standard); the deal carries from the invitation to the creator when they accept.

Share Knowledge with every creator, skills included. A skill is a folder: a folder holding a file named SKILL is a skill, its SKILL file says how to do the task and its other files support it. Share whole folders with `--knowledge-folder-ids '["<folder-id>"]'` (up to 10; ids from `oxygen knowledge folders list --json`) and single files with `--knowledge-slugs '["product"]'` (up to 30; slugs from `oxygen knowledge index --json`), on `oxygen ugc programs create` or `update`. A shared folder is live: every file in it and its subfolders reaches creators, files added to it later included, and a file moved out stops being shared. Nothing is copied, so a change reaches creators who already joined at once. Only these files are shared; other master knowledge stays private, and creators read them read-only. They load into each creator's AI: the creator's Workspace Copilot lists them in its context on every turn (a skill as one group, SKILL first) and opens what a task needs, and program drafts use them, following their guidance on how a post is built while the creator's voice decides tone. A slug or folder that does not exist (or an archived page) is refused with `ugc_knowledge_page_not_found` or `ugc_knowledge_folder_not_found`, naming what is missing, and nothing is saved. In the web app, **Files for creators → Choose files** in the program panel is a checkbox tree of your Knowledge: check a folder to share it whole, or single files, and search by name.

Preview an invitation email with `oxygen ugc creators invite --program-id <id> --email <creator-email> --json`. The preview shows the exact recipient, sender, subject, body and expiry, plus `html`, the Oxygen-branded email as the creator receives it (the Oxygen mark and the program's logo, the message, an Accept button and the join link), and creates no invitation or email. Its `reply_to` is the inviting teammate's own address, so a creator's reply reaches the brand. An address on a placeholder domain (example.com, test.com, `.test`, `.invalid`) is refused with `ugc_invitation_placeholder_email` on every path, `--link-only` included, and nothing is created: no one can receive the email there or sign in with it to accept. Ask the person for the creator's real address; never invent one. To write it in the organizer's words, add `--email-subject "..."` (up to 200 characters) and `--email-message "..."` (up to 3,000); the Accept button and join link are always added below the message, so never paste the link yourself. Changing either needs a new preview before `--approved`. The join link in a preview is not live: no invitation exists until the approved send creates it, so never hand a preview link to anyone (use `--link-only` for a shareable link). With communication authorization for that recipient and email, repeat the same command with `--approved --preview-token <exact-preview-token>` to create the invitation and send it. Sending uses 0 credits. To create only a shareable link, use `--link-only`: it creates the invitation immediately, with no preview or approval token, sends no email and costs 0 credits (a link-only invitation that sponsors previews first; see Sponsorship). Never call link-only creation while claiming you emailed someone.

To invite several creators at once, pass `--emails "a@example.com,b@example.com"` (or a JSON array; 1–50, duplicates removed) instead of `--email`. The preview shows one representative email plus every recipient in `recipients`; a recipient with a `pending_invitation_id` already has a pending invitation and is not emailed again. Approve with `--approved --preview-token <exact-preview-token>` and the same `--emails`: a different list is refused. Each recipient gets their own link, and `results` reports each one's `status` (`sent`, `failed`, `unknown`, `sending` or `not_sent` with an `error`); report each honestly and never resend a `sending` or `unknown` one. `--link-only` with `--emails` returns one link per recipient and sends nothing.

Read `oxygen ugc creators list --program-id <id> --json` for existing invitations and their persisted `email_delivery` status. To email an existing pending invitation, preview `oxygen ugc creators send-invite --program-id <id> --invitation-id <id> --json`, then repeat with `--approved --preview-token <exact-preview-token>` under the user's communication authorization. This also supports an explicit resend after its cooldown. It replaces the previous link and preserves the invitation's expiry. Accepted, revoked or expired invitations cannot be sent. A failed attempt may be retried after reviewing the error; `sending` or `unknown` must not be retried blindly. Never recreate the invitation as a retry workaround.

Read back `invitation.email_delivery`: `sent` means accepted by the email provider, not confirmed inbox delivery. A send the email service refused ends `ok: false` with `ugc_invitation_email_not_sent` (exit 1). The invitation exists anyway: it is in `error.details.invitation`, with its `invite_url`. For a wrong address, revoke it and invite the right one; never resend it unchanged. `ugc_email_outcome_unknown` means do not resend. A batch with any unsent recipient ends `ugc_invitation_batch_incomplete`, with every recipient in `error.details.results`. MCP equivalents are `oxygen_ugc_invite_create` (`email` or `emails`; optional `posting_target`; `send_email` defaults to true; false is link-only; `sponsor` true sponsors on accept), `oxygen_ugc_creator_target_update` and `oxygen_ugc_invite_send`, both with exact `preview_token` plus `approved` for sending. In the web app, **Creators → Invite creators** opens a side panel: creator emails, posts per creator (prefilled with the program standard; a different number is that creator's own deal), then **Preview email → Send** or **Links only**; the **Sponsor their LinkedIn accounts** switch adds the sponsorship cost to the review. Its pending invitations show delivery status, **Sponsored** when they sponsor on accept, **Send email** or **Resend**, and their deal. The creators list has a **Posts** column to change a creator's deal. **New program** and **Edit program** open one side panel with the product domain, the Markdown brief and posts per creator.

Creators learn product facts only from the program brief and the Knowledge files shared above; each creator drafts from their own topic.

Program lifecycle, all free and provider-free. Rename or edit settings with `oxygen ugc programs update --program-id <id> --name "New name" --json`. Start a second program from an existing one with `oxygen ugc programs duplicate --program-id <id> --name "Acme Analytics" --json`; the copy is active and carries the settings, shared page slugs and posting target, never creators, invitations, posts or sponsorship. Without `--name` it keeps the source's name, because creators read the name. Stop a program with `oxygen ugc programs archive --program-id <id> --json`: pending invitations are revoked, open applications are declined, sponsorship renewals are cancelled, shared history stays readable, and `oxygen ugc programs restore --program-id <id> --json` re-activates it without restoring removed creators, revoked invitations or cancelled sponsorships. Permanent removal is only possible while no creator has ever joined: `oxygen ugc programs delete --program-id <id> --json` previews the pending invitations, creators and enrolled posts and reports `deletable`; add `--approved` to delete. A program with creators returns `ugc_program_in_use`, and archive is the way to retire it.

## Creators

In a creator workspace, start with `oxygen ugc memberships list --json`. It returns active programs that this workspace has joined; use the exact participation ID when a post is saved into a program.

Read the files a program shares with `oxygen ugc knowledge list --program-id <id> --participation-id <id> --json`; follow their returned links. They are the brand's live, read-only files; a file inside a shared skill folder carries `skill` (open the skill's SKILL file first) and a file from a shared folder carries its `folder` path. `oxygen knowledge index --json` lists your own pages plus `shared_pages`, every file your programs share; open one with `oxygen knowledge page get <ugc:reference> --json`. Your Workspace Copilot already sees them in its context and opens them for program work.

In the web app, open the invitation, then use **Join a creator program → Participation workspace** to select your workspace or create one. The invitation stays open through that choice. Fill **Your LinkedIn profile URL** and choose **Post approval**; **Accept invitation** joins the selected workspace. A LinkedIn profile joins a program once: accepting or applying with a profile that already joined it, from any workspace, is refused with `ugc_linkedin_already_joined`. Open **My posts → New post**. **Your profile and connection → Open Accounts** opens the LinkedIn connection screen; return to select the matching account and **Save connection and approval**. In the CLI, `oxygen senders list --json` lists existing connections without a provider call.

A program is private (invitation only) unless the brand passes `--visibility public` on `oxygen ugc programs create` or `update`; a public program is listed in every creator's Discover with its name, product link, logo, a brief excerpt and its deal. As a creator, `oxygen ugc programs discover --json` lists public programs with `joined` and your `application` status; apply with `oxygen ugc programs apply --program-id <id> --message "<short note>" --json` (note up to 600 characters, one pending application per program, 0 credits). A declined application is final: applying to that program again, from any workspace with the same LinkedIn profile, is refused with `ugc_application_declined`, though the brand can still invite you. It uses the LinkedIn URL on your profile; if there is none, the error `ugc_linkedin_url_required` says so: ask the person for their LinkedIn profile URL (never guess), then save it with `oxygen ugc profile update --linkedin-url <url>` or pass `--linkedin-url` to apply, which also saves it to your profile. Follow the application with `oxygen ugc applications list --json`. As the brand, `oxygen ugc applications list --program-id <id> --json` shows who applied (pending first); `oxygen ugc creators approve --program-id <id> --application-id <id> --json` adds the creator at once and emails them (`approval_email.status` reports whether it went out; the approval stands either way), and `oxygen ugc creators decline ...` declines without an email; the applicant cannot apply to that program again, but the brand can still invite them. MCP: `oxygen_ugc_get` views `discover` / `applications`, `oxygen_ugc_application_create`, `oxygen_ugc_application_decide`. In the web app: **UGC → Creator → Discover programs → Apply**, and the brand's **Creators** tab lists pending applications with Approve and Decline.

A public program can let creators join without the brand's approval (Tim, 2026-10-09): `oxygen ugc programs update --program-id <id> --visibility public --join-policy automatic --json` (MCP `join_policy: "automatic"`). `oxygen ugc programs get --program-id <id> --json` then returns `join_policy` and `join_url` (`<app>/ugc?join=<program-id>`), the link to share: it opens the visitor's Creator side, through sign-in or sign-up, with the program's join panel. The link opens only while the program is public and active. Automatic join is a public-program setting: `--join-policy automatic` on a private program is refused with `ugc_join_policy_requires_public`, and `--visibility private` turns it off. With automatic join, `oxygen ugc programs apply --program-id <id> --json` (the note is optional) answers `joined: true` with the new `participation` (its `sender_account_id` is already the LinkedIn account the creator posts from, when that is clear; otherwise set it with `creators update --sender-account-id`), the same membership a brand's approval creates: the creator approves their own posts, nobody is sponsored and joining grants no engagement authority. Every other rule holds: one LinkedIn profile joins a program once, a declined applicant cannot apply again, and an archived program refuses. With `approval` (the default) the answer is `joined: false` and the application waits for the brand. `oxygen ugc programs discover --program-id <id> --json` reads the one program a join link names, with its `join_policy`. In the web app: **Edit program → Who can join → Public: creators join automatically**, and **Copy join link** in the program's menu or on its **Creators** tab.

As a creator, `oxygen ugc memberships list --json` lists the programs this workspace joined, each with `posting_target` (your deal: your own, else the program's standard; `own_deal` says which), `posting_target_progress` for the current period and `published_posts`. These are your numbers only; a creator never sees other creators'. Keep a short creator profile the brands you joined can read: `oxygen ugc profile update --topics "B2B sales, outbound" --audience "Early-stage B2B founders" --linkedin-url <your-profile-url> --json` (up to 10 topics, audience up to 200 characters; `--topics` replaces the list, `--audience ""` and `--linkedin-url ""` clear), and read it back with `oxygen ugc profile get --json`. MCP: `oxygen_ugc_get` view `memberships` / `creator_profile` and `oxygen_ugc_creator_profile_update`. A program only becomes choosable for a post once your LinkedIn account is connected to it; in the web app, **Publishing → UGC → Creator** holds the profile and one LinkedIn account for all your programs.

Before accepting, read the invitation with `oxygen ugc creators invitation --token <token> --json`: it returns the program, the invited email (masked), the posting deal and `can_accept`, with `reason` and `message` when this account or workspace cannot accept (`wrong_account`: sign in with the invited email; `own_workspace`: switch to your own creator workspace; `revoked`, `expired` or `accepted`: ask the organizer for a new invitation; `program_archived`). Accept only the intended invitation, in your own creator workspace: `oxygen ugc creators accept --token <token> --json` uses the LinkedIn URL on your profile. Pass `--linkedin-url <profile-url>` only when there is none; it is then saved to your profile. `ugc_linkedin_url_required` means ask the person; never guess. The creator approves each post by default; pass `--approval-mode delegated` only when the creator explicitly authorizes that program's operators to edit, approve and schedule their enrolled posts. When the brand sponsors on accept, the invitation read includes `sponsorship` with its `message`, and accepting returns `sponsorship.status` (`sponsored`, `already_sponsored`, or `skipped` with a `reason`) plus a `notice`; after `skipped`, ask the brand to sponsor you before connecting LinkedIn, because until then a connected account reserves credits from your own workspace. A notice that the sponsorship is not confirmed yet (no `sponsorship` in the response) means nothing was decided: accepting the same invitation again retries it, or the brand can sponsor you. The web accept screen shows the same invitation details and has no approval choice. A creator can participate in multiple programs independently.

Reuse the existing LinkedIn connection. Discover the Accounts/senders commands, connect once through the hosted connection flow if needed, then use `oxygen ugc creators update --participation-id <id> --sender-account-id <id> --json`. Never create a second physical connection just because another program sponsors a seat.

Start without LinkedIn by saving creator-written preferences and up to five real examples: `oxygen ugc voice save --participation-id <id> --body "Short, concrete sentences" --writing-examples '["A sentence I actually wrote."]' --json`. This private provisional Knowledge draft costs 0 credits and makes no provider call. Read it with `oxygen ugc voice get --participation-id <id> --json`; when replacing it, pass the returned revision as `--expected-revision`.

Voice profiles and import progress are private to the creator workspace; organizer reads are refused with `ugc_voice_private`.

Preview voice import with `oxygen ugc voice import --participation-id <id> --json`. Preview makes no provider/model call and does not require a bound sender or interactive-session approval. Read the exact all-retrievable scope and credit ceiling, then connect the matching LinkedIn account and execute only from the signed-in creator session with `--approved --max-credits <ceiling>`. Inspect durable imports with `oxygen ugc voice get --participation-id <id> --json`; queued is not completed. Read `date_range`, counts and `coverage` honestly: “all retrievable” can still end at provider exhaustion or a credit/provider limitation. Resume only when `can_resume` is true, using `oxygen ugc voice import --participation-id <id> --import-id <id> --approved --max-credits <total-ceiling> --json`; the ceiling includes credits already used.

In the web app, open **My posts → New post → Learn your writing voice**. Under **Start with your own words**, fill **Writing preferences** and **Your writing examples (optional)**, then choose **Save provisional voice · 0 credits**. To import LinkedIn history instead, choose **Preview voice import** and review the preview before approving its credit ceiling. **Refresh voice progress** reads the import status; **Review your voice page** opens the canonical inferred guide when available. The same single synthesis creates separate private `creator-writing-patterns` and `creator-writing-examples` Knowledge drafts; examples are bounded real quotations with their imported source URLs. Later synthesis creates reviewable proposals for each existing page rather than overwriting creator edits. Review stored daily post metrics in the program's **Results** view.

Ask the creator what they want to post about, including any personal experience they want to share, and preview drafting with `oxygen ugc posts draft --participation-id <id> --topic "How our team cut onboarding from two weeks to three days after switching" --json`. The draft is written in the creator's voice and follows the program's shared files on how a post is built; product facts come only from the program brief and those files, and personal experience or endorsements come only from the topic text. If the result returns `needs_answers`, ask the creator those questions and draft again with a fuller topic. That first call without `--approved` is a free preview (0 credits) that returns `request_id` and `estimated_credits`, the figure to approve. The paid draft runs only from the creator's own workspace, by repeating the same command with `--request-id <preview-request-id> --approved --max-credits <ceiling>`; an organizer with delegated approval may preview but can never spend the creator's credits. Replaying that ID returns the original operation or completed result without a new dispatch. After a timeout, error or incomplete state, keep the ID and run `oxygen ugc posts draft-status --participation-id <id> --request-id <preview-request-id> --json`. `started` or `generating` is only the last persisted state, not proof work is still running; `effect_unknown` may already have spent or produced an effect. Do not retry or change IDs while the original outcome is uncertain. A new ID starts a new paid request. Never invent a creator's experience or turn a research guess into testimony. To tag the brand's LinkedIn company page in a post, write `@<handle>` from its `linkedin.com/company/<handle>` URL; approval shows the page each tag resolved to.

The creator chooses **Personal** or one **Program** before the first save. Ordinary Publishing remains personal. To create and enroll in one step, run `oxygen publishing posts create --publish-at <ISO-time-with-timezone> --sender <sender-account-id> --text "Creator-authored copy" --ugc-participation-id <id> --json`. This always saves an unapproved draft; `--approved` or a scheduled status is refused. Creators may also enroll an existing stored Publishing post from their participation's connected LinkedIn sender. In the web app, use **My posts → Add an existing post**. In the CLI, discover candidates with `oxygen publishing posts list --provider linkedin --sender <sender-account-id> --limit 50 --json`; follow `next_cursor` with `--cursor <cursor>` and the same filters. These reads use stored posts and make no provider call. Enroll the chosen post from the creator workspace with `oxygen ugc posts enroll --participation-id <id> --post-id <source-post-id> --json`. Enrollment shares that post with the program; it does not approve or publish it. A master cannot enroll a creator's unrelated posts, even with delegated approval authority.

Read posts with `oxygen ugc posts list --program-id <id> --json` and retain each post's `enrollment_id`, `enrollment_version` and `source_revision`. Always bind edits and approvals to the current enrollment: `oxygen ugc posts update --program-id <id> --post-id <source-post-id> --enrollment-version <n> --content-text "Reviewed text" --json`. Schedule through the same command with `--scheduled-for <ISO-time-with-timezone>`; when the creator schedules their own post from their signed-in session, add `--approve true` and the call also approves exactly the text it saves, so no separate approval follows (the web editor's Schedule and Post Now do this). Save edits first; content changes invalidate previous approvals. An operator acting under delegation approves the current saved post with `oxygen ugc posts approve --program-id <id> --post-id <source-post-id> --enrollment-version <n> --source-revision <reviewed-source-revision> --approved --json` only with creator or delegated authority. Brands cannot require approval of creator posts: the creator's approval, or the organizer's when the creator delegated it, is the only content gate. Read back the post's status: an approval is not proof of publication.

Before publication begins, the creator can remove the program enrollment with `oxygen ugc posts remove --program-id <id> --post-id <source-post-id> --enrollment-id <active-enrollment-id> --source-revision <current-source-revision> --json`. Removal retains an ordinary personal draft and immutable program history. The organizer's post list shows a removed enrollment with `status: removed` (its `projection` keeps the last shared snapshot); it leaves the calendar and analytics. A later enrollment receives a new `enrollment_version` and needs fresh approvals; never reuse an earlier version or receipt.

To leave the entire program, the creator uses `oxygen ugc creators update --participation-id <id> --status revoked --json`. Revocation stops future cross-workspace sharing, publishing, metric refresh and engagement under that participation. The creator keeps their posts, private history and voice in their own workspace; the organizer keeps previously shared snapshots and receipts. The creator loses access to the program's shared Knowledge. Existing paid credit lots remain through their paid period; read back any `billing_cancellation_pending` notice. Revocation does not erase published social posts or retained history. Neither this workspace nor the same LinkedIn profile from another workspace can rejoin the same program. To remove only one post while staying, use `ugc posts remove` instead.

## Sponsorship and amplification

Sponsorship preview and confirmation require the same signed-in master workspace administrator, using a CLI user-session profile or web session. Organization API keys cannot perform either step. Previewing is free and creates no charge or entitlement.

Preview exact participation IDs with `oxygen ugc sponsorship preview --program-id <id> --participation-ids '["participation-id"]' --json`. The preview's `funding` says how the workspace pays:

- `credits`: each sponsored creator costs one connected LinkedIn account, a monthly credit reservation (`monthly_credits_per_creator`) charged to the sponsoring workspace's billing owner and never to the creator. A creator another program already sponsors adds nothing (`reservation_credits: 0`); a creator who has not connected LinkedIn yet starts when they connect (`reservation_starts`). The creator receives no credit grant. Check `spendable_after`; when it is negative, `next_step` names the top-up.
- `stripe` (card): each master program pays a sponsored seat and a monthly 10,000-credit grant for each sponsored creator, even when another program sponsors that creator. Grants are usable creator-wide in Oxygen.

Sponsorship does not transfer ownership of the creator or connection.

Read the returned quote and recurring cost. Confirm only with explicit billing authorization using `oxygen ugc sponsorship confirm --program-id <id> --participation-ids '["participation-id"]' --quote <exact-quote-string> --approved --json`. Never invent or reconstruct the quote. A credit confirmation starts the reservations at once and returns `insufficient_credits` (exit 7) with the top-up when the balance cannot carry them; a card confirmation returns a checkout URL per creator. If a sponsor's balance later cannot cover a renewal, the creator's LinkedIn account pauses sending and disconnects after the grace period, as any unfunded account does; `oxygen billing commitments --json` shows the reservation.

To sponsor creators as you invite them, add `--sponsor` to `oxygen ugc creators invite` (MCP `sponsor: true`); it needs the same signed-in administrator and credit funding (under card funding it returns `ugc_invite_sponsor_credits_only`: invite, then sponsor after they join). The preview's `sponsorship` block shows the live price as `monthly_credits_per_creator` (one connected LinkedIn account's reservation: 3,400 credits a month at current prices), `monthly_credits_at_most` for all invited creators (a creator another program already sponsors adds nothing), `starts: when_each_creator_connects_linkedin`, and `spendable_after_at_most`, your spendable balance if every invited creator's first month were reserved; when the balance falls short it adds `shortfall_credits` with `next_step`. Nothing is reserved until a creator accepts and connects LinkedIn, and nothing is charged if they never do. Revoking a pending invitation withdraws its sponsorship; after acceptance, stop it with `oxygen ugc sponsorship cancel` (MCP `oxygen_ugc_sponsorship_cancel`). Approving the invitation (`--approved --preview-token`) approves that sponsorship, and is refused with `insufficient_credits` (exit 7) before anything is created or sent when the balance cannot carry every invited creator's first month. With `--link-only --sponsor` the first call previews and creates nothing; repeat it with `--approved --preview-token <token>` and the same recipients and deal to create the links. When a creator accepts, they are sponsored within the approved price; if the price rose, the approver is no longer an administrator or the balance falls short, the creator still joins and the sponsorship is skipped with its `reason`, and you can sponsor them from the Creators tab. `creators list` shows each pending invitation's `sponsorship` (`on_accept`, `monthly_credits`, and `result` once accepted).

A signed-in master admin can do the same in the web app: the program's Creators tab shows each creator's sponsorship, and Sponsor opens the same quote before anything is reserved or charged, and Stop renewal previews the cancellation.

Read sponsorship with `oxygen ugc sponsorship get --program-id <id> --participation-id <id> --json`. In a creator workspace this returns only that creator's program allowance and `funding`, unexpired credit lots (card sponsorships only), own unrestricted wallet balance, paid-through/cancellation state, and the organizer's exact read/edit/approval boundary. To stop one renewal, a master previews `oxygen ugc sponsorship cancel --program-id <id> --participation-id <id> --json`, then repeats with `--approved` from a signed-in master admin only after reviewing that scope. Cancellation preserves participation and whatever was paid through the current period; an unpaid (pending) sponsorship stops at once, its checkout closes and nothing is charged (`renewal: stops_now`, `paid_period_credits_preserved: false`); read back `cancellation_pending` when provider confirmation still needs reconciliation. A credit sponsorship stops without any card-provider call, and the creator's LinkedIn account is the creator's own from its next renewal.

Amplification is optional, starts disabled, and is limited to the program's enrolled published posts. Discover `oxygen ugc amplification save --help`. Require exact opted-in participant sender IDs, allowed actions (`reaction`, `comment`, `repost`), action count per post, delay bounds and a credit ceiling per rolling 24-hour cycle. Comments or reposts also require `--sender-voice-pages '{"<sender-account-id>":"<active-voice-page-id>"}'` for every acting sender; the voice page belongs to that master account's workspace context. Enabling needs explicit approval and `--acknowledge-risk` (LinkedIn may restrict accounts used for automated engagement); at most 12 actions per post; no blanket engagement on arbitrary URLs. Read the current policy and paginated immutable receipts with `oxygen ugc amplification get --program-id <id> --json` and its `next_cursor`.

UGC amplification excludes the post author. For a creator reacting or commenting on their own post, discover `oxygen engagement react --help`, `oxygen engagement comment --help` or `oxygen publishing comments --help`; these are separate public actions with their own preview and approval. Check any cost before approving.

To post one specific comment on one creator's program post, the organizer workspace previews it with `oxygen ugc posts comment schedule --program-id <id> --post-id <source-post-id> --sender-account-id <organizer-sender-id> --text "Exact comment" --at <ISO-time-with-timezone|now> --json`. The preview is free, saves nothing, and shows the post, acting account, exact text and time. Only after the operator approves that exact comment, repeat it with `--approved` from a signed-in session; it posts publicly on LinkedIn at that time within the account's active hours and daily comment limit, and costs 0 credits. The post does not have to be live yet; live means published through OXYGEN, with a LinkedIn post OXYGEN has confirmed. On a draft, in-review or scheduled post, or one that shows as published without a confirmed LinkedIn post, the comment waits: the preview `notice` says "Waits until this post is live on LinkedIn, then posts as …", the comment reads `waiting_for_post: true`, and it posts once the post is live, never before its time. If the post is still not live 14 days after that time, the comment fails ("The post never went live on LinkedIn.") and is never posted; a post published outside OXYGEN may never be confirmed. A removed post cannot take a comment. Read `scheduled_comments` (status `scheduled`, `posting`, `posted`, `failed` or `cancelled`, plus `waiting_for_post`) with `oxygen ugc posts list --program-id <id> --post-id <source-post-id> --json`. Cancel only while it is still `scheduled`, including while it waits: `oxygen ugc posts comment cancel --program-id <id> --comment-id <id> --json`. A `failed` comment is never retried automatically; check the post on LinkedIn before scheduling it again.

Peer engagement is a separate creator-owned grant. A master admin may permit it for the program with `oxygen ugc programs update --program-id <id> --peer-engagement-enabled true --json`; this switch does not opt in any creator. In the creator workspace, read `oxygen ugc peer-amplification get --participation-id <id> --json`, then preview the creator's exact sender, actions and caps with `oxygen ugc peer-amplification save --participation-id <id> --sender-account-id <id> --actions '["reaction"]' --enabled true --max-actions-per-post 1 --max-credits-per-cycle 20 --json`. Comment or repost also needs that creator's `--voice-page-id`. Repeat with the returned `--expected-policy-version <n>`, `--approved` and `--acknowledge-risk` only after creator authorization. The creator wallet, including available sponsored credits, pays. Joining, sponsorship and delegated publishing approval confer no peer-engagement permission.

Peer `effect_unknown` receipts follow the same evidence-only rule. Preview `oxygen ugc peer-amplification reconcile --participation-id <id> --action-id <id> --outcome applied --evidence '<exact JSON>' --json`, then add `--approved` only after review. It records immutable observed evidence without a provider call or retry.

An `effect_unknown` receipt is never safe to retry. Preview an observed resolution with `oxygen ugc amplification reconcile --program-id <id> --action-id <id> --outcome applied --evidence '<exact JSON>' --json` (or use `not_applied`); confirmation requires a signed-in operator and `--approved`. Applied evidence binds the target provider post and object, and comments/reposts require the exact observed text. Reconciliation appends one immutable observation, makes no provider call, and authorizes no retry.

## Program analytics

Read the bounded stored calendar with `oxygen ugc calendar list --program-id <id> --date-from <inclusive> --date-to <exclusive> --json`, each an ISO instant or a `YYYY-MM-DD` date meaning that day's 00:00 UTC (so `--date-to 2026-12-21` includes December 20); ranges are UTC, at most 42 days, and continue with `next_cursor` as `--calendar-cursor`.

Read `oxygen ugc analytics get --program-id <id> --json` for complete program and creator aggregates plus paginated `post_performance`. Continue post rows with `next_post_cursor`; aggregate totals still cover all scoped enrolled posts. Each dimension includes up to 30 retained daily snapshots. Those values are cumulative metrics observed on that date with measured-post coverage, not daily engagement deltas. Enrolled published program posts automatically receive daily metric collection through their creator's connected account while the participation and program remain active. No manual generic Publishing sync is needed; opening UGC analytics reads stored results.

`creators` lists every active creator of the program, including ones with no posts yet, with their `creator` name, picture and `headline`. When the program has a posting target or the creator has their own deal, each active creator's `posting_target_progress` measures that creator's effective target (`own_deal: true` when it is their own) and counts posts published in its current calendar period in UTC (the calendar month, or the ISO week from Monday): `period_start` and `period_end` are its first and last day, `published` against `target`, and `hit` once published reaches the target. A `total` target counts every post published since the program began: `period_start` is the program's creation day and `period_end` is null. It is null when neither the program nor the creator has a target, and for a creator who left the program. A pending invitation is not yet a creator here; read its deal from `creators list`.

For one enrolled post's retained facts, use `oxygen ugc posts history --program-id <id> --post-id <source-post-id> --enrollment-version <n> --json`. Public comments, metric history and amplification actions paginate independently through `next_comments_cursor`, `next_metrics_cursor` and `next_actions_cursor`; publication receipts remain attached. Follow every non-null cursor before calling the retained history complete. A removed and re-enrolled post has distinct retained versions.

Collection depends on account availability, provider limits and background retry/backoff. Providers may omit impressions or other metrics: unavailable/null means unknown, not zero. Check each metric’s measured-post coverage and sync freshness before comparing results. Keep provider receipts, source post IDs and run state available for diagnosis.
